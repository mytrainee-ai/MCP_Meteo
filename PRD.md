# PRD v2.0 — Weather AI Agent

**Статус:** Готов к передаче Codex  
**Тип продукта:** AI-агент погоды с веб-чатом  
**Основной интерфейс:** Streamlit  
**Язык интерфейса:** русский  
**Среда:** Windows, Python 3.14  
**LLM:** OpenAI Responses API  
**MCP SDK:** 2.3.0

---

## 1. Цель проекта

Разработать веб-приложение Weather AI Agent, в котором пользователь общается с AI-агентом через браузер.

Агент должен понимать естественные вопросы о погоде, самостоятельно выбирать MCP-инструменты, получать фактические погодные данные и формировать ответы на русском языке.

**Главный принцип:** OpenAI LLM принимает решения, Python выполняет вызовы инструментов, MCP предоставляет погодные данные.

### 1.1. Примеры запросов

- Какая сейчас погода в Москве?
- Будет ли завтра дождь в Париже?
- Покажи прогноз на три дня в Берлине.
- А какая температура будет вечером?
- А завтра?
- Какая погода в другом городе?

### 1.2. Исходное состояние

В проекте `MCP_Meteo` уже существует работающий прототип `weather_agent.py`.

Успешно проверены:

- Подключение к удалённому MCP-серверу.
- Получение списка MCP-инструментов.
- Вызов `geocode_location`.
- Вызов `get_weather_forecast`.
- Преобразование MCP-инструментов в OpenAI function tools.
- Работа OpenAI Responses API.
- Автоматический выбор инструментов моделью.
- Возврат результатов MCP модели.
- Генерация ответа пользователю.

**Требование:** сохранить работающий прототип и использовать его как основу для рефакторинга.

## 3. Архитектура

```text
Пользователь
    |
    v
Браузер
    |
    v
Streamlit Chat UI
    |
    v
Session State / Conversation Manager
    |
    v
AI Agent
    |
    v
OpenAI Responses API
    |
    | function_call
    v
Tool Adapter
    |
    v
MCP Client
    |
    | tools/call
    v
Open-Meteo MCP Server
    |
    v
Результат MCP
    |
    v
AI Agent
    |
    v

```

### 3.1. Разделение ответственности

**Streamlit UI:** отображает чат, принимает сообщения, показывает состояние обработки запроса.

**Conversation Manager:** хранит историю диалога в пределах браузерной сессии.

**AI Agent:** выполняет цикл OpenAI Responses API и function calling.

**Tool Adapter:** преобразует схемы инструментов, проверяет аргументы и обрабатывает результаты MCP.

**MCP Client:** подключается к удалённому серверу и выполняет вызовы инструментов.

**Config:** управляет переменными окружения и настройками приложения.

## 4. Требования к веб-интерфейсу

### FR-01. Чат в браузере

Использовать Streamlit.

Обязательные компоненты:

- `st.title()` — заголовок приложения.
- `st.chat_message()` — отображение сообщений.
- `st.chat_input()` — ввод пользовательского вопроса.
- `st.session_state` — хранение состояния сессии.
- `st.spinner()` или `st.status()` — индикатор обработки запроса.

### FR-02. Интерфейс пользователя

На странице должны присутствовать:

1. Заголовок **Weather AI Agent**.
2. Краткое описание возможностей.
3. Область переписки.
4. Поле ввода сообщения.
5. Кнопка «Очистить чат».
6. Индикатор обработки запроса.
7. Понятные сообщения об ошибках.

Интерфейс должен поддерживать русский язык и корректно отображаться на компьютере и смартфоне.

### FR-03. Отображение сообщений

Сообщения пользователя и агента должны визуально различаться.

При отправке сообщения:

1. Сразу показать сообщение пользователя.
2. Отобразить индикатор обработки.
3. Выполнить agent loop.
4. Показать ответ модели.
5. Сохранить обновлённую историю.

Не показывать пользователю сырые JSON-ответы MCP в обычном режиме.

### FR-04. Очистка чата

Кнопка «Очистить чат» должна удалять историю сообщений и контекст LLM текущей сессии.

После очистки агент не должен помнить ранее выбранный город.

## 5. Память диалога

### FR-05. Память в пределах сессии

Использовать `st.session_state`.

Пример:

**Пользователь:** Какая погода в Москве?

**Агент:** Сейчас в Москве...

**Пользователь:** А завтра?

**Агент:** Завтра в Москве...

Второй вопрос должен относиться к Москве.

### FR-06. Раздельное состояние

Хранить отдельно:

- Сообщения, отображаемые в чате.
- Историю, передаваемую OpenAI Responses API.
- При необходимости текущий подтверждённый город.
- Состояние обработки запроса.

История Streamlit UI не должна автоматически считаться полной историей OpenAI.

### FR-07. Жизненный цикл

Память существует только в пределах активной Streamlit-сессии.

Не использовать базу данных или постоянное хранилище в MVP.

Не допускать смешивания историй разных пользователей или браузерных сессий.

### FR-08. Управление контекстом

Ограничивать размер истории.

При сокращении контекста сохранять согласованность элементов Responses API, особенно пар `function_call` и `function_call_output`.

При ошибке запроса не оставлять в истории незавершённые вызовы инструментов.

## 6. Требования к MCP

### FR-09. Подключение

Использовать удалённый MCP-сервер:

`https://weather.chukai.io/mcp`

Для MCP SDK 2.3.0 использовать подтверждённый интерфейс:

```python
async with streamable_http_client(MCP_URL) as (
    read_stream,
    write_stream,
):
    async with ClientSession(
        read_stream,
        write_stream,
    ) as session:
        await session.initialize()
```

Транспорт возвращает два значения.

### FR-10. Инструменты

Использовать только разрешённые инструменты:

- `geocode_location`
- `get_weather_forecast`

Получать их описание через `session.list_tools()`.

### FR-11. Совместимость SDK

Использовать фактические поля:

```python
tool.input_schema
result.structured_content
result.content
result.is_error
```

Не использовать неподтверждённые camelCase-поля.

### FR-12. Обработка результатов

Если `structured_content` отсутствует, извлекать JSON из текстовых блоков `content`.

Если `is_error=True`, считать вызов ошибочным.

Не передавать результат ошибки модели как успешный погодный прогноз.

---

## 7. Требования к OpenAI

### FR-13. Responses API

Использовать `AsyncOpenAI` и `client.responses.create()`.

Модель определяется переменной `OPENAI_MODEL`.

### FR-14. Tool calling

Агент должен:

1. Получить список разрешённых MCP-инструментов.
2. Преобразовать `input_schema` в OpenAI function tools.
3. Передать инструменты модели.
4. Получить `function_call`.
5. Разобрать аргументы.
6. Проверить имя инструмента и аргументы.
7. Вызвать MCP.
8. Сериализовать результат.
9. Передать `function_call_output` с соответствующим `call_id`.
10. Повторять цикл до финального ответа или достижения лимита.

### FR-15. Безопасность

Обязательно:

- Allowlist инструментов.
- JSON Schema validation аргументов.
- Ограничение числа шагов.
- Ограничение количества вызовов инструментов.
- Тайм-ауты внешних запросов.
- Ограничение размера данных, передаваемых модели.
- Запрет выполнения произвольного кода, полученного от LLM.

### FR-16. Ограничения

Начальные настройки:

- Максимум 6 шагов agent loop.
- Максимум 10 MCP-вызовов на запрос.
- Конфигурируемый тайм-аут 30 секунд для внешних операций.

При достижении лимита приложение должно сообщать об этом пользователю.

---

## 8. Работа с погодой

### FR-17. Геокодирование

Использовать `geocode_location`.

Из результатов получать координаты, страну и часовой пояс.

### FR-18. Неоднозначные города

Если найдено несколько подходящих населённых пунктов и контекст не позволяет выбрать один, агент должен попросить уточнение.

Нельзя автоматически считать первый результат геокодирования правильным.

### FR-19. Прогноз

Использовать `get_weather_forecast`.

Поддерживать:

- Текущую погоду.
- Прогноз на завтра.
- Прогноз на несколько дней.
- Вопросы об осадках.
- Вопросы о температуре и ветре.

Использовать фактическую схему инструмента и учитывать ограничения сервера.

### FR-20. Достоверность

Агент не должен придумывать погодные данные.

Если данных недостаточно, сообщать об этом.

Учитывать часовой пояс города и не путать текущие наблюдения с прогнозом.

### Требования к реализации

`streamlit_app.py` должен содержать только логику интерфейса и связывания компонентов.

Вся бизнес-логика AI-агента должна находиться в `src/`.

Не дублировать код MCP и OpenAI в Streamlit-приложении.

Streamlit перезапускает скрипт при взаимодействиях. Поэтому Codex должен корректно организовать асинхронные вызовы и жизненный цикл MCP-соединения, не сохраняя объекты, привязанные к закрытому event loop, в `st.session_state`.

- Преобразование MCP-схем.

## 12. Нефункциональные требования

### NFR-01. Простота

Проект должен оставаться понятным начинающему Python-разработчику.

Не использовать сложные фреймворки оркестрации без необходимости.

### NFR-02. Надёжность

Ошибки отдельных запросов не должны завершать приложение.

### NFR-03. Безопасность

Не хранить API-ключи в исходном коде.

Не показывать технические секреты пользователям.

### NFR-04. Производительность

Не выполнять ненужные LLM- и MCP-вызовы.

Не допускать блокировки интерфейса бесконечными операциями.

### NFR-05. Разделение сессий

История одного пользователя не должна быть доступна другому.

Не использовать глобальную общую переменную для хранения переписки всех пользователей.

### NFR-06. Наблюдаемость

Предусмотреть DEBUG-режим для разработчика.

В обычном режиме не показывать технические данные пользователю.
